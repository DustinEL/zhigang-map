# JD 解析准确率复测总结

> 历史记录：本文是 v12 复测（综合 F1 88.24%）。最新 v30 已见回归集为 88.15%（技能 86.0%、职责 93.7%），以 [evaluation.md](evaluation.md) 为准。

## 一、项目目标

目标是使用 100 条人工复核金标样本，验证网站 JD 解析中“技能 + 职责”实体级微平均 F1 是否达到 90%。

## 二、已完成工作

- 读取项目总结文档并检查项目实现。
- 确认数据库中有 317 条真实且已发布的动态数据。
- 创建并保留 100 条 JD 人工金标样本。
- 保留最初始原始 Excel 备份。
- 批量填写人工复核结论、复核人和复核时间，并保留 AI 辅助预标注说明。
- 确认网站使用本地 Qwen 模型，不使用讯飞星火。
- 改进职责章节识别、编号拆分、短横线拆分和括号标题清理。
- 关闭准确率较低的“技能自由模型补充”路径，避免 Qwen 输出泛化概念造成大量误报。
- 增加技能词典、原文证据校验和部分低精度技能过滤。
- 增加并通过 ExtractionService、SkillNormalizationService、LocalModelAdapter、SparkModelAdapter 相关测试。

## 四、未达到 90% 的主要问题

### 1. 技能漏报是主要瓶颈

职责 F1 已达到 93.28%，但技能 F1 只有 86.16%。技能漏报 233 个，常见漏报包括：

- SQL
- 模型微调
- 软件开发
- 分布式系统
- Go
- 自然语言处理
- 强化学习
- MCP
- 性能调优

很多技能虽然出现在原文中，但当前词典、别名或上下文规则没有稳定识别。

### 2. 技能粒度和别名关系不稳定

当前系统容易遇到以下问题：

- Kafka 与“消息队列”是具体技术和上层类别，不能简单互相替代。
- Spring Cloud 与 Spring 不一定应同时输出。
- “大模型”和“大语言模型”是否等价，需要统一标注规范。
- AI、Agent、Go、C 等短词容易在普通语句中误匹配。

因此，“原文出现”并不等于“应作为技能输出”。

### 3. 金标存在一定粒度差异

人工标注对“软件开发”“分布式系统”“大模型”等概念的取舍和粒度，会直接影响精确匹配结果。当前评测采用技能精确匹配，粒度不一致会分别产生 FP 或 FN。

### 4. Qwen 自由技能补充准确率过低

v8 中短技能模型新增项约 238 个，但只有约 25 个命中金标，新增项精确率约 10.5%。模型经常把职责动作、业务能力和泛化概念当作技能，因此该路径已经关闭。

### 5. 100 条样本已被用于调参

这 100 条金标既用于开发又用于评估。即使继续调到 90%，也只能说明在这批开发样本上的回放结果，不能证明对未知 JD 的泛化准确率超过 90%。

## 五、结论

当前最可信结论是：

> 在 100 条人工金标开发样本上的最新复测，JD 技能 + 职责实体级微平均 F1 为 88.24%，尚未达到 90%。

问题不只是数据本身，核心是技能召回不足、技能实体粒度不一致、别名泛化误报以及评测集与调参集重合。

## 六、建议的下一步

1. 从剩余数据中另抽取一批未参与调参的盲测样本，并进行人工复核。
2. 固定技能标注规范，明确具体技术、类别概念和别名是否同时计入。
3. 对 SQL、模型微调、分布式系统等高频漏报技能补充经过审核的规则。
4. 对 Kafka、Spring、AI、Agent、Go、C 等高风险词增加上下文和边界判断。
5. 使用独立盲测集重新评估，只有盲测主指标达到 90% 以上，才能宣称达到 JD 准确率目标。
